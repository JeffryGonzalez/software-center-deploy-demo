# Orchestration with Kubernetes

Docker Compose is useful locally. Kubernetes is what runs this in production — and the conceptual jump between the two is smaller than it looks.

Compose and Kubernetes both answer the same questions:
- What containers should run, and from which images?
- What environment variables does each one get?
- How do they find each other on the network?
- Where does persistent data live?

The difference is that Kubernetes answers those questions across a cluster of machines, with health checking, self-healing, rolling updates, and resource management built in. The vocabulary is different, but the intent maps closely.

## The Cluster

For this workshop, a shared Kubernetes cluster is provided. You won't install or configure anything at the cluster level — it's already running Traefik as the ingress controller using the Kubernetes Gateway API. All you need is `kubectl`.

Verify you can reach the cluster:

```bash
kubectl cluster-info
kubectl get nodes
```

## The Namespace

Everything for this app lives in the `software-center` namespace. The namespace is already created — you can verify with:

```bash
kubectl get namespace software-center
```

All `kubectl` commands going forward target this namespace. You can either pass `-n software-center` each time, or set it as your default context:

```bash
kubectl config set-context --current --namespace=software-center
```

## The Manifests

All Kubernetes manifests are in the `k8s/` directory:

```
k8s/
├── namespace.yaml    # the namespace (already applied)
├── api.yaml          # PVC + API Deployment + Service
├── bff.yaml          # BFF Deployment + Service
├── frontend.yaml     # Frontend Deployment + Service
└── httproute.yaml    # Gateway API HTTPRoute (Traefik ingress)
```

### Images

The manifests reference images on Docker Hub under `jeffrygonzalez/`:

| Image | Built from |
|-------|-----------|
| `jeffrygonzalez/sc-api:latest` | `./api` |
| `jeffrygonzalez/sc-frontend:latest` | `./frontend` |
| `jeffrygonzalez/sc-bff:latest` | `./bff` |

`imagePullPolicy: Always` is set on each container — this tells Kubernetes to pull a fresh copy of the image every time a pod starts, rather than using a cached version. For a workshop with `latest` tags this is important; in production you'd use immutable version tags instead (see [CI/CD](./60-ci-cd.md)).

kubectl apply -f k8s/frontend.yaml

kubectl apply -f k8s/httproute.yaml

## What Each Manifest Does

### `api.yaml` — three resources in one file

**PersistentVolumeClaim**: requests 1 GB of storage from the cluster. The cluster provisions it and keeps it alive independently of the pod. If the API pod is deleted and recreated, it reattaches to the same PVC and picks up exactly where it left off.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: catalog-db
spec:
  accessModes:
    - ReadWriteOnce    # one node can mount this at a time
  resources:
    requests:
      storage: 1Gi
```

`ReadWriteOnce` is the right access mode for SQLite — only one pod mounts it, so only one pod can write. This is also why the Deployment has `replicas: 1`. (See [Infrastructure](./30-infra.md) for the full explanation.)

**Deployment**: describes the pod — which image, what environment variables, which volume to mount, how much CPU/memory to request and limit.

```yaml
volumeMounts:
  - name: db-storage
    mountPath: /data
volumes:
  - name: db-storage
    persistentVolumeClaim:
      claimName: catalog-db
```

The volume mount connects the PVC to `/data` inside the container, where the API expects to find `catalog.db`.

**Service**: a stable internal address for the API. Pods come and go (restarts, rollouts), but the Service's DNS name — `catalog-api.software-center.svc.cluster.local`, or just `catalog-api` from within the same namespace — never changes. This is what the BFF's YARP config points at.

### `frontend.yaml`

A Deployment and Service for the nginx container. No volumes needed — static files are baked into the image. The readiness probe hits `/` to confirm nginx is up before the pod is added to the Service's endpoint list.

### `bff.yaml`

A Deployment and Service for the .NET BFF. Notice the port mapping: the container listens on **8080** (`ASPNETCORE_URLS=http://+:8080`), but the Service exposes **port 80**. Traefik reaches the Service on port 80; the Service forwards to port 8080 on the pod.

The YARP configuration in `appsettings.json` already has the right cluster addresses for Kubernetes (`http://catalog-api:3000` and `http://catalog-frontend`) — no environment variable overrides are needed in the manifest.

The readiness probe hits `/health` — the single health check endpoint in `Program.cs`. Kubernetes will not send traffic to the pod until this probe returns 200.

### `httproute.yaml` — Gateway API ingress

This is how external traffic reaches the cluster. The Kubernetes Gateway API is a newer, more expressive alternative to the classic `Ingress` resource. Traefik implements it.

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: software-center
  namespace: software-center
spec:
  parentRefs:
    - name: traefik-gateway
      namespace: traefik
      sectionName: websecure    # the HTTPS listener on the gateway
  hostnames:
    - software.hypertheory-labs.com
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /
      backendRefs:
        - name: catalog-bff
          port: 80
```

The `parentRef` attaches this route to the `traefik-gateway` Gateway (which lives in the `traefik` namespace) and specifically to its `websecure` listener — the HTTPS entrypoint. Traefik handles TLS termination; traffic inside the cluster is plain HTTP.

The route matches everything (`/`) and sends it to the `catalog-bff` Service on port 80. The BFF then applies its own routing rules — `/api/**` to the API, everything else to the frontend.

Compare this to Compose, where service discovery was by container name on a private network. In Kubernetes, it's Service names — same concept, different vocabulary.

## Verifying the Deployment

```bash
# Watch pods come up
kubectl get pods -w

# Check all resources in the namespace
kubectl get all

# Check the PVC is bound
kubectl get pvc

# Check the HTTPRoute was accepted by Traefik
kubectl get httproute

# Follow logs from the API pod
kubectl logs -l app=catalog-api -f

# Follow logs from the BFF
kubectl logs -l app=catalog-bff -f
```

Once all pods show `Running` and `1/1` ready, open https://software.hypertheory-labs.com.

## Updating a Deployment

When you push a new image and want Kubernetes to pick it up:

```bash
# Force the deployment to pull the latest image and restart pods
kubectl rollout restart deployment/catalog-api
kubectl rollout restart deployment/catalog-bff
kubectl rollout restart deployment/catalog-frontend

# Watch the rollout
kubectl rollout status deployment/catalog-bff
```

This triggers a rolling update — Kubernetes starts a new pod, waits for it to pass the readiness probe, then terminates the old one. Zero downtime, no manual intervention.

## Tearing Down

```bash
# Remove everything except the namespace and PVC
kubectl delete -f k8s/bff.yaml
kubectl delete -f k8s/frontend.yaml
kubectl delete -f k8s/api.yaml
kubectl delete -f k8s/httproute.yaml

# Remove the PVC (this deletes the database)
kubectl delete pvc catalog-db
```
